Everything in Chapters 1–8 assumed the compiler would turn a sharded program into well-scheduled MXU work, DMAs and collectives. This chapter opens that box. It follows a small sharded MLP through every stage, using real compiler output, then covers the two front ends that feed the same compiler: JAX and TorchTPU.

## The stages

The Scaling Book's summary of the TPU stack <Cite id="SB9" at="#a-thousand-foot-view-of-the-tpu-software-stack" />:

1. **Python and JAX** trace a function into a **jaxpr**, JAX's own intermediate form.
2. `jax.jit` lowers the jaxpr to **StableHLO**, a versioned, platform-independent MLIR dialect. Sharding annotations travel with it.
3. **XLA** converts StableHLO to **HLO** and runs its passes:
   - sharding propagation and SPMD partitioning;
   - fusion;
   - layout assignment;
   - memory-space assignment between HBM and VMEM;
   - scheduling.
   The optimized HLO is what a profile shows.
4. The TPU backend lowers HLO to **LLO**, a low-level IR that programs the TensorCore directly: copies between memories, pushes into the systolic arrays, DMA scheduling.
5. LLO becomes machine code, loaded into the TensorCore's instruction memory.

Pallas kernels enter as custom calls at stage 3 and are compiled by Mosaic (Chapter 10). The TPU backend of XLA, stages 4–5, ships in the closed-source `libtpu` <Cite id="X-arch" />.

Each stage can be printed: `jax.make_jaxpr(f)(*args)`, `jax.jit(f).lower(*args).as_text()` for StableHLO, and `.compile().as_text()` for optimized HLO <Cite id="J-aot" />. `XLA_FLAGS=--xla_dump_to=DIR` writes every HLO pass to disk <Cite id="X-dumps" />.

## What you control, and what you do not

**You control:**

- **Shardings** of inputs and outputs, and intermediate constraints via `jax.lax.with_sharding_constraint`. The Scaling Book calls adding constraints to steer propagation "compiler tickling", and estimates it is "about 60% of JAX parallel programming in the automatic partitioning world". The usual symptom of bad propagation is an unexpected AllGather taking most of a profile <Cite id="SB10" at="#auto-sharding-mode" />.
- **Layouts.** Passing `AUTO` input layouts to `jax.jit` lets XLA pick, avoiding relayout copies <Cite id="SB9" at="#how-to-read-an-xla-op" />.
- **Rematerialization** policies via `jax.checkpoint`.
- **Buffer donation** via `donate_argnums`, which lets outputs reuse input buffers. This is how KV caches update without copies.
- **XLA flags**, passed on TPU through the `LIBTPU_INIT_ARGS` environment variable, the convention MaxText and Google's recipes use <Unverified />. Examples:
  - the latency-hiding scheduler (`xla_tpu_enable_latency_hiding_scheduler`);
  - async collective fusion;
  - the windowed-einsum threshold for collective matmul;
  - scoped VMEM limits (`xla_tpu_scoped_vmem_limit_kib`);
  - memory-space-assignment tuning.

  The OpenXLA flags guide lists them <Cite id="X-flags" />.
- **Pallas kernels**, for anything the compiler does not generate well (Chapter 10).

**You do not control:** TPU code generation, fusion decisions beyond what flags expose, VLIW bundle scheduling and VMEM allocation inside fusions. The backend is closed, so these are visible only in their effects, through profiles and HLO dumps.

<GpuAnalogy title="GPU analogy: CUDA Graphs and torch.compile">
<p>A CUDA Graph records a DAG of already-compiled kernels and their launches, then replays it. That removes CPU launch overhead, but it does no cross-kernel optimization; changing the graph's structure requires re-instantiation <Cite id="N-graphs" s="§4.2" />. `torch.compile` with Inductor goes further: it fuses operations and generates Triton kernels for each graph it captures.</p>
<p>XLA compiles the whole step as one program. In one optimization problem it chooses fusion, the layout of every array, which arrays sit in VMEM and when, and when each collective starts relative to compute. The result is closer to "CUDA Graph plus Inductor plus a global memory planner plus collective scheduling" in one pass.</p>
</GpuAnalogy>

<AnalogyBreaks>
<p>The cost of whole-program compilation is that the whole program must be known. Shapes are compile-time constants. Data-dependent control flow becomes `lax.cond` or `while_loop` with fixed shapes. A shape not seen before means minutes of compilation rather than a slower kernel. On a GPU, eager mode is the fallback for whatever a graph cannot capture. On a TPU with JAX there is no eager fallback in production; TorchTPU's eager modes, below, are the first serious attempt at one.</p>
</AnalogyBreaks>

## Sharding: GSPMD, Shardy and three modes

**GSPMD** introduced the model JAX still uses <Cite id="P-GSPMD" s="§3–4" />. You write a single-device program and annotate a few tensors with shardings. The compiler propagates shardings to every other tensor, then rewrites the program into one per-device program with collectives inserted. The paper reported 50–62% compute utilization up to 2,048 TPUv3 cores.

**Shardy** replaced GSPMD's propagation as JAX's default in version 0.7.0 <Cite id="J-log" />. It is MLIR-based, uses named mesh axes instead of device-assignment tensors, and distinguishes open dimensions (which propagation may shard further) from closed ones. It also adds propagation priorities. Its annotations are the `sdy.sharding` attributes in the StableHLO listing above <Cite id="X-shardy-jax" />.

JAX now offers three ways to say how a program is sharded <Cite id="SB10" at="#how-does-parallelism-work-in-jax" /> <Cite id="J-shard" />:

| Mode | View of arrays | You specify | Collectives |
|---|---|---|---|
| Auto (`AxisType.Auto`) | global | input and output shardings, optional constraints | inserted by the compiler |
| Explicit (`AxisType.Explicit`, "sharding in types") | global; `jax.typeof(x)` shows `float32[8@X,512@Y]` | sharding is part of each array's type; ambiguous ops must say `out_sharding` | inserted by the compiler, as JAX's rules specify |
| Manual (`jax.shard_map`) | per device | `in_specs`, `out_specs` | written by you: `psum`, `all_gather`, `ppermute`, `all_to_all` |

Explicit mode moves sharding errors from profile time to trace time. Multiplying arrays whose contracting dimensions are both sharded is ambiguous: the result could be AllReduced or ReduceScattered. JAX refuses to guess:

## TorchTPU

TorchTPU is Google's native PyTorch backend for TPUs, built with Meta's PyTorch team. It was described in April 2026 and open-sourced on 2026-10-20 <Cite id="T-blog1" /> <Cite id="T-oss" />. Google's docs state that "TorchTPU replaces PyTorch/XLA" <Cite id="D-pytorch" />, and PyTorch/XLA's repository is archived on 2026-11-15 <Cite id="T-xla" />.

### Where it plugs in

TorchTPU registers as an out-of-tree PyTorch backend on the `PrivateUse1` dispatch key, renamed `tpu`. Importing it enables `torch.device("tpu")`. Tensors are ordinary PyTorch tensors, with "no subclasses, no wrappers" <Cite id="T-how" />. That is the main difference from torchax, whose tensors are a subclass wrapping JAX arrays, and from PyTorch/XLA, whose `xla` device held lazy tensors.

### How an op executes

When an ATen op dispatches to `tpu`, TorchTPU does not run it. It creates a **deferred op** holding a **StableHLO builder**; `aten::mul` becomes a `stablehlo.multiply` under construction. The returned tensor's storage points at it. PyTorch semantics that StableHLO lacks are emulated: views and in-place mutation are handled by decomposing and inverting views, since StableHLO is single-assignment <Cite id="T-how" />.

When deferred ops are compiled and run depends on the mode <Cite id="T-exec" />:

| Mode | Behaviour | Use |
|---|---|---|
| Strict eager (default) | each op compiled on its own at `-O1` and dispatched asynchronously | correctness, debugging, unchanged PyTorch code |
| Debug eager (`TORCH_TPU_LAUNCH_BLOCKING=1`) | host waits after every op | locating the op that fails |
| Fused eager (`TORCH_TPU_DEFER_AND_FUSE=1`) | ops accumulate until a sync point or a repeated loop is detected, then compile as one `-O2` graph | eager code with much of compiled performance |
| `torch.compile(model, backend="tpu")` | TorchDynamo captures an FX graph, emitted as one StableHLO program and compiled by XLA | production |

Two details matter for performance reasoning:

- **No Inductor.** TorchTPU states that it "does not use TorchInductor". The FX graph goes to XLA, so the fusion and scheduling of this chapter apply unchanged <Cite id="T-exec" />.
- **Fused eager's speedup is reported inconsistently.** The launch blog says 50% to more than 100% over strict eager; the docs say up to 50% <Cite id="T-blog1" /> <Cite id="T-exec" />.

Execution goes through PjRT and libtpu on a background thread, so errors can surface after the op that caused them. Compiled programs are cached at three levels: in the process, in shared memory on the machine, and in a remote persistent store. Keys cover the graph, shapes, compiler options and library versions. A first compile can take minutes; the caches make it a one-time cost <Cite id="T-exec" />.

### Distributed: the SPMD handshake

TorchTPU provides a `tpu_dist` process group. DDP, FSDP2, DTensor and SimpleFSDP run on it, and `torch.tpu.distributed.topology_aware_mesh()` builds a DeviceMesh aligned with ICI rings. Collectives lower to StableHLO collective ops compiled by XLA, "no separate library like NCCL" <Cite id="T-dist" />.

This creates a problem JAX never had. XLA's collectives assume every device runs the same program (SPMD). PyTorch's distributed model is one process per device, and ordinary PyTorch code often branches on rank: rank 0 logs, or only some ranks do an extra step. That is MPMD. If two ranks compile different programs around a collective, the collective can deadlock or mismatch. TorchTPU's default is to compile collectives in isolation, which is safe but prevents fusing them with neighbouring compute. The **SPMD handshake** lets ranks confirm they are running identical programs before fusing across collectives. It is controlled by `TORCH_TPU_SPMD_HANDSHAKE_STAGE` (`OFF`, `COMPILE_STAGE` or `DISPATCH_STAGE`), and the `@spmd_safe` decorator marks code known to be rank-independent <Cite id="T-dist" />. JAX avoids the problem by construction: one traced program describes all devices.

### Kernels and status

Pallas kernels are registered with `torch.tpu.pallas.jax_op` and called as ordinary ops. The April blog named the API `custom_jax_kernel`, so check the version you install. Tokamax kernels are usable directly, and Helion support is experimental <Cite id="T-kern" />. Google's PyTorch blog reports two results <Cite id="T-pt" />:

- Qwen3-MoE-235B trained on 8,192 TPU v7 chips at 27.1% MFU.
- A 30B model prefilling at 59% MFU on one chip.

A "52% MFU on 8,192 chips" figure circulating in press coverage does not appear in the primary sources <Unverified />.

### Four ways PyTorch code reaches a TPU

| | PyTorch/XLA (deprecated) | torchax | TorchTPU eager | TorchTPU `torch.compile` |
|---|---|---|---|---|
| Tensor type | lazy `xla` tensors | `torch.Tensor` subclass holding a `jax.Array` | plain tensors on `PrivateUse1` | plain tensors |
| Graph capture | trace until `mark_step` | `jax.jit` traces through `__torch_dispatch__` | none (strict), or deferred regions (fused) | Dynamo FX graph |
| IR handed to XLA | HLO via lazy IR | StableHLO via jaxpr | StableHLO per op or region | StableHLO per graph |
| Parallelism | SPMD mode | JAX shardings | `tpu_dist`, DDP, FSDP2, DTensor | same |
| Kernels | XLA custom calls | Pallas directly | Pallas via `jax_op`, Tokamax | same |

Sources: <Cite id="T-xla" />, <Cite id="R-torchax" />, <Cite id="T-how" />, <Cite id="T-exec" />.
